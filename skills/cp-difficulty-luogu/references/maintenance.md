# 专家经验与版本维护

正式评分只加载 `SKILL.md`、`rubric.md` 和 `expert-rules.json`。当前经验库为空，这是框架版本，没有声称已经获得专家验证的通用规则或准确率提升。

维护者在仓库 `data/difficulty/expert/` 分别维护 `cases.jsonl` 与 `experiences.jsonl`。单题历史标签和解释只用于开发。记录必须包含来源、适用条件、局限、反例和人工确认状态。旧版已确认的五个 K/T/I 单轴数字仅保留历史事实，不代表其他轴、整题标签或通用规则得到确认。

最小流程：

1. 用 `experts.py new-case` 生成反馈表，填写题目身份、家族、无标签完整材料的路径与哈希、真实原生等级及来源、专家解释、可选相邻题比较和模型错误。专家核对材料后记录 reviewer 与日期，再 `add-case` 录入。0 可作为待补标签保存，不能成为正式经验的有效标注来源。
2. `experts.py distill` 只导出开发专用请求。将请求交给一个 LLM，归纳少量候选经验，明确哪些观察困难及其条件，不许从某题等级直接推出算法到档位的映射。不自动调用模型，不自动更新正式 Skill。
3. 用 `new-rule` 的格式保存候选。检查来源解释是否支持结论，寻找反例，填写适用条件、局限与反例检查记录。`add-rule` 保留候选状态。
4. 人工审核后，在经验记录中将 `confirmation.status` 改为 `confirmed`，填写 reviewer、reviewed_on。候选、拒绝项、未复核来源不能进入正式库。
5. 人工选择已确认规则，复制完整记录到 `expert-rules.json`，更新 Skill、rubric 和经验库版本，记入仓库版本记录。`experts.py check-release --data ...` 核验正式库与已确认原记录一致。此命令只检查，不写 Skill。
6. 冻结版本与提示后，使用新的家族隔离评测集比较同模型基线。已查看标签并用于诊断的评测题永久登记为开发数据，不通过改名恢复独立身份。

`confirmed` 表示人工确认规则及来源，不等于独立 Benchmark 已验证其增益。每次发版分别记录规则审核状态与评测状态。经验过多时合并重复项，删除没有适用价值的项，不累积题目标签表。
